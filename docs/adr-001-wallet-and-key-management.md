# ADR 001: Wallet and Key Management

## Status

Accepted. This decision was made at the start of the project before any code was written. This document was revised once during the documentation phase to address gaps identified in a second-pass review. After any code begins depending on this ADR, future changes will be handled by superseding ADRs rather than by editing this document, in keeping with the convention that accepted ADRs preserve their historical record.

## Context

The bot trades on Solana using a wallet whose private key authorizes all spending. This key is the cryptographic root of trust for our entire trading operation. Any code path that has access to the key can sign transactions that move funds out of the wallet, and any compromise of the key allows an attacker to drain the wallet completely and irreversibly. Solana transactions cannot be reversed once confirmed, so there is no recovery path if the key is compromised and used maliciously.

The project also uses several other secrets that are sensitive but not as catastrophic as the wallet key. These include the Helius API key, the Telegram bot token, and any third-party API keys we use for data enrichment. These secrets allow access to services we depend on, but losing them does not directly result in financial loss the way losing the wallet key does. They still need protection, but the security model around them can be lighter.

We need to decide how the wallet key is generated, where it is stored, how it is loaded into the running bot, who or what can access it during operation, how we handle the case of suspected compromise, and what backup or recovery mechanisms we maintain. We also need to decide how the secondary secrets are managed, with appropriate consistency between the two systems but appropriate proportionality of effort.

The threat model we are designing against includes remote attackers attempting to access our running server through network exploits or compromised dependencies, local attackers who somehow gain access to the server filesystem or running process memory, supply chain attacks where a dependency we trust turns out to be malicious, operational mistakes such as accidentally committing secrets to version control or pasting them into chat clients, and the natural attrition of secrets becoming stale or accidentally exposed over time. We also account for the possibility that the bot itself might be compromised through a vulnerability in our code or a dependency, requiring that the wallet adapter remain defensive even against malicious calls from within the same process.

## Decision

The wallet key is generated locally on the developer's machine using a trusted Solana wallet client, never on a hosted system or shared environment. It is generated specifically for this bot and used for nothing else. The wallet that holds the key is funded only with money we can afford to lose, with the bulk of any holdings kept in a separate cold wallet that the bot has no access to. Funds are transferred from the cold wallet to the bot wallet only in amounts appropriate for active trading, with the cold wallet remaining the primary store of value.

The key is stored as a base58-encoded string in an environment variable named `SOLANA_PRIVATE_KEY` that is loaded at process startup. The environment variable is set through a `.env` file on the deployment server, which is excluded from version control through the project's `.gitignore` file. The `.env` file has filesystem permissions restricted to the bot's user account, with no read access for other users on the system. The bot runs as a dedicated unprivileged user account that exists only for running this process, with no shell access and no other purposes. The setup of this user account is a hard requirement of the security model rather than an optional refinement, and the operational security ADR documents the specific procedures for creating and configuring it.

The infrastructure layer of the codebase contains a single module called the wallet adapter that holds the key in memory after loading. No other module in the system has access to the key. The adapter exposes only operations that need the key, specifically the operation to sign a given transaction. The adapter does not expose the key itself, does not log the key, does not serialize the key for any purpose, and does not provide any introspection method that would reveal the key. Code that needs to sign a transaction calls the adapter's signing method with the unsigned transaction and receives back the signed version.

The signing method on the wallet adapter performs validation before signing. It checks that the transaction is structurally well-formed, that the instruction list is consistent with our expected operations, that the spending limits configured for the bot are not exceeded by the transaction, and that the destination accounts are not on a blocklist of known malicious addresses. Only after these checks pass does the adapter actually sign. This validation provides a backstop against bugs in upstream code that might otherwise produce a transaction that signs successfully but does something unintended.

The wallet adapter logs every signing event to a dedicated audit log, separate from the general application log. The audit entry records the timestamp, the transaction signature once the transaction is submitted, the destination accounts, the SOL value being moved, and the calling code path. The audit log is append-only and is rotated separately from the general logs. This audit trail serves both for debugging and for incident response if a compromise is later suspected.

The Helius API key, the Telegram bot token, and other secondary secrets follow the same general pattern but with reduced ceremony. They are loaded from environment variables, held by the relevant infrastructure adapters, and never logged. They do not require the validation layer the wallet key does, because they do not directly authorize spending. They still must not appear in version control or in any output that could be read by unauthorized parties.

The system maintains the ability to swap out the wallet key in case of suspected compromise. The procedure is to generate a new wallet on a clean machine, transfer any remaining funds from the old wallet to the new one in a single transaction signed manually rather than by the bot, update the environment variable on the deployment server, and restart the bot. The old wallet should be considered permanently compromised after this point and never used again. The Helius and Telegram credentials should be rotated through the respective services' provider interfaces if they are believed to have been exposed alongside the wallet key.

We do not encrypt the key on disk in this project. The protection model relies on filesystem permissions and the principle that the deployment server is the trust boundary. If an attacker can read the `.env` file, they have already compromised the system in ways that encrypting the file would not meaningfully defend against, because they could simply log keystrokes or process memory to capture the key when it is loaded. We accept this tradeoff because adding disk encryption introduces complexity and an additional secret to manage, without proportionally improving security against the threats that actually concern us. This decision should be revisited if we ever expand to a deployment model where the disk is shared or backed up to systems we do not fully control.

We do not use a hardware wallet for this bot. Hardware wallets provide stronger protection because the key never leaves the device, but they require interactive confirmation for every signing operation, which is incompatible with an automated trading bot. The compromise we accept is that the key lives in software on a server we control, with the protections described above. This is the correct choice for this use case but should be revisited if the wallet ever holds enough value that the calculus changes.

The bot runs with kernel protections that prevent the key from being written to disk through unintended channels. Specifically, core dumps are disabled for the bot process. If the bot crashes, the kernel does not produce a core file containing the process memory, which would otherwise capture the wallet key alongside everything else. This is configured through the operating system's resource limits at the time the bot is launched. The general application log captures crash information at a higher level than memory contents, giving us debugging information without exposing secrets.

The bot does not spawn child processes during normal operation. Any process that inherits the bot's memory or environment also inherits access to the wallet key, which would defeat the isolation model. If a future feature requires running external commands, the implementation must explicitly clear the sensitive environment variables before spawning the child process, and must not pass any reference to the wallet adapter to the child. This is a strict design rule that any code review must enforce.

The wallet adapter monitors validation failures and responds to suspicious patterns. A small number of validation failures over time may simply indicate bugs in upstream code. A burst of validation failures in rapid succession, particularly involving transactions that resemble drain attempts, indicates either a serious bug or an active attack. When this pattern is detected, the adapter halts further signing operations and emits a high-priority alert through the interface layer. The bot enters a paused state where existing positions are still monitored but no new signing operations occur. The pause must be cleared through manual intervention, requiring the operator to acknowledge the situation before normal operation resumes. This circuit breaker pattern provides a final defensive layer against scenarios where multiple other defenses have failed.

The bot supports a remote pause command through the Telegram interface that immediately halts all signing operations. Issuing this command from any authenticated session causes the wallet adapter to refuse all subsequent signing requests until manually unpaused. This provides a kill switch for situations where the operator suspects compromise but cannot immediately access the server to investigate. The command is authenticated using the same Telegram user whitelist that protects all other commands, ensuring an attacker who has not also compromised the operator's Telegram cannot cause spurious pauses or unpauses.

The bot handles process restarts and software updates through a clean shutdown procedure. When the bot receives a termination signal, the wallet adapter completes any in-flight signing operations, refuses new ones, and clears the wallet key from memory before the process exits. This minimizes the window during which the key exists in a process that may be subject to debugging or memory inspection. On startup, the new process loads the key fresh from the environment, so there is no persistent state related to the key beyond what is in the .env file itself.

## Consequences

The wallet adapter becomes the single most security-sensitive module in the codebase. Its implementation requires careful review, and any changes to it require correspondingly careful review. The validation layer inside the adapter is defense in depth, but it is also a place where bugs could either weaken the protection or break legitimate operations. Tests for the adapter must cover both sides of this, ensuring that valid transactions sign correctly and invalid transactions are rejected.

The fact that no other module has access to the key means that anything requiring a signature must go through the adapter. This is a deliberate funnel. It means we have exactly one place to audit when reasoning about who can spend funds. It also means that the adapter's interface needs to be expressive enough to handle every signing case we encounter. If we discover a case the adapter does not support, we add a new method to the adapter rather than working around the funnel.

The audit log creates a complete record of every transaction the bot ever signs. This is valuable for operations and incident response, but it also means the audit log itself contains sensitive information about our trading patterns. It must be protected with the same care as the application's other sensitive data, including being excluded from any version control or backup that does not have appropriate protection.

The decision not to encrypt the key on disk means the entire security model depends on the deployment server not being compromised. This places weight on the operational security of the server, which is addressed in a separate ADR. The decision is defensible only because we have the operational discipline to keep the server secure. If that discipline weakens, the decision should be revisited.

The decision not to use a hardware wallet means the key is potentially exposed to any process running with sufficient privileges on the server. We mitigate this by running the bot as an unprivileged user, by keeping the server otherwise minimal, by disabling core dumps, by refusing to spawn child processes, and by keeping only as much value in the wallet as the bot needs for active trading. The bulk of any meaningful holdings remains in a separate cold wallet that this entire ADR does not apply to.

The procedure for rotating the wallet in case of compromise requires manual intervention. This is intentional. Rotating a wallet is a rare and serious operation, and it should require human judgment rather than being automated. The cost is that the rotation cannot happen instantly. The benefit is that we cannot accidentally rotate the wallet through a bug.

The validation failure circuit breaker introduces a new failure mode where the bot can become paused unexpectedly if the threshold is poorly tuned. We accept this because the alternative is no defense against rapid-fire attacks, and a paused bot is a far better failure than a drained wallet. The threshold values for triggering the circuit breaker should be conservative enough that legitimate operation never trips it, but tight enough that an actual attack is interrupted quickly. These values are configuration parameters that we tune based on observation during the early phases of the project.

The remote pause capability means the Telegram bot token has slightly higher security significance than it would otherwise have, because compromise of the Telegram bot now allows an attacker to disable the trading bot's defenses by spamming pause commands. This is mitigated by the user whitelist on incoming commands, which means an attacker would need to compromise both the Telegram bot token and the operator's Telegram account to abuse the pause functionality. The risk is acceptable because the same compromise would expose other operational risks anyway.

The clean shutdown behavior means that the bot cannot be killed instantly without potentially leaving in-flight transactions in an unclear state. This is the right tradeoff because cleanly closed signing sessions are more predictable than abruptly terminated ones, but it does mean operations like emergency restarts may take a few seconds longer than a hard kill. The shutdown timeout is bounded so that the bot cannot hang indefinitely if something prevents clean shutdown.

## Alternatives Considered

We considered storing the key encrypted on disk with a passphrase entered at startup. This would provide some protection against an attacker who reads the disk but does not have access to the running process. We rejected this because the threat scenario it defends against is narrow and requires us to manage a passphrase separately. In practice, an attacker who can read arbitrary files on the server can almost certainly also read process memory or set up keylogging, defeating the encryption when the passphrase is entered. The complexity is not justified by the marginal security improvement.

We considered using a cloud secrets management service such as AWS Secrets Manager or HashiCorp Vault. These services provide audit logging, automatic rotation, and access control. We rejected them because they introduce a runtime dependency on an external service, which complicates the deployment for a personal project. The bot would need credentials to access the secrets service, which becomes its own secret to manage. The benefit is real for production systems handling significant value but excessive for a personal trading bot at our scale.

We considered using a hardware security module or hardware wallet for signing operations. This would provide the strongest protection possible because the key never leaves the device. We rejected it because hardware signers require interactive confirmation, which is incompatible with automated trading. There are some hardware solutions designed for automated signing, but they are expensive and complex to integrate. The cost is not justified at our scale.

We considered using a multi-signature wallet that requires two or more keys to sign a transaction. This would mean an attacker who compromises one key still cannot drain the wallet. We rejected it because Solana's native multi-signature support is less mature than Bitcoin's or Ethereum's, and the implementation would require either a custom on-chain program or a third-party service that adds complexity. The single-key model with limited wallet contents is sufficient for our threat model.

We considered allowing the strategy layer or other modules to hold a reference to the wallet adapter directly, rather than going through the event-driven flow. This would simplify the code in some places. We rejected it because we want the strategy layer to be unable to sign transactions even if it has bugs or is somehow compromised. The strict separation between strategies and the wallet is a deliberate security boundary.

We considered making the validation failure threshold trigger an automatic wallet rotation, where the bot generates a new key and migrates funds without human intervention. We rejected this because automatic key rotation in response to a possible attack creates its own attack vector, where an attacker who can trigger validation failures can also trigger key rotations and potentially redirect the migration. Manual rotation requires deliberate human action and is therefore safer despite being slower.

We considered exposing administrative operations through a separate authenticated channel rather than the Telegram interface, for example a small HTTP endpoint with mutual TLS authentication. We rejected this because adding another authentication system creates more attack surface for marginal security benefit. The Telegram interface is already authenticated and already secured, so reusing it is appropriate.

## Implementation Notes

The wallet adapter module belongs in the infrastructure layer at a path like `src/infrastructure/wallet/walletAdapter.ts`. It exposes a narrow interface defined by a type, with the implementation hidden behind that interface. The interface is what other modules import; the implementation is constructed once at startup and passed to whatever needs it through dependency injection.

The validation logic inside the adapter is extracted into a separate validation module to keep the adapter itself focused. The validation module takes an unsigned transaction and configuration parameters, and returns either a confirmation that the transaction is acceptable or an error describing why it is not. This separation makes the validation logic testable in isolation.

The circuit breaker logic is a third extracted module, distinct from the validation module, that tracks the rate of validation failures and decides when to enter the paused state. Keeping it separate from validation means we can tune the circuit breaker behavior without touching the validation rules themselves.

The audit log uses a dedicated log file, separate from the application log. The format is structured JSON, one entry per line, with a fixed schema. The file is created by the bot at startup if it does not exist, with restrictive permissions. Log rotation is handled by the operating system through standard mechanisms rather than being implemented in the bot itself.

Core dump prevention is configured through Node.js process limits at startup. The specific call sets the resource limit for core file size to zero before any sensitive memory is allocated. This is one of the first things the bot does on startup, before loading any keys, to ensure the protection is in place before there is anything to protect.

The signal handling for clean shutdown is registered early in the startup process. The handlers respond to SIGTERM and SIGINT by initiating the shutdown sequence. The shutdown sequence has a hard timeout, after which the process exits even if cleanup is incomplete, to prevent the bot from hanging on shutdown. Cleanup includes flushing the audit log, closing network connections, and clearing the wallet key from memory by overwriting the buffer that holds it.

Test coverage for the wallet adapter must include the validation rules, the signing operation, the audit logging, the circuit breaker behavior, the shutdown sequence, and the rejection of child process spawning. The signing operation tests should use a test keypair generated within the test, never the real key. The audit logging tests should verify that every code path that signs also logs. The circuit breaker tests should verify both that it triggers under attack patterns and that it does not trigger under normal operation.

When working with Claude Code on this module, the security requirements should be communicated clearly. Generated code that bypasses the validation layer or that adds new methods exposing the key in any form should be rejected. Generated code that spawns child processes anywhere in the codebase should trigger careful review of whether the wallet key environment variable is being properly cleared. The principles of least privilege and defense in depth apply to the implementation, not just the design.
