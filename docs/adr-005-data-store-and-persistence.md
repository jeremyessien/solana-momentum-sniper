# ADR 005: Data Store and Persistence

## Status

Accepted, 14 May 2026. This decision was made after the Phase 1 detection-and-observation pipeline went live end-to-end on `dev` but before any persistent storage was added to the bot. After any code begins depending on this ADR, future changes will be handled by superseding ADRs rather than by editing this document, in keeping with the convention that accepted ADRs preserve their historical record.

## Context

The bot's pipeline is live end-to-end on the `dev` branch as of this writing. Detection observes Pump.fun program logs and emits `NewTokenLaunchDetected` events. Enrichment subscribes to those events and produces `TokenAnalysisCompleted` events carrying the full RugCheck report. The activity tracker subscribes to the same on-chain stream and emits `TokenTradeObserved` for every trade against a tracked mint, plus a single `TokenTrackingClosed` summary when tracking terminates. The Telegram interface subscribes to the lifecycle-relevant events and forwards them to the operator. The structured logger writes everything to journald as JSON.

What is missing is durable storage. Every event flowing through the bus is consumed in the moment and then gone. The architecture document repeatedly says "the data store subscribes" for each event in the catalog. No such store exists.

The cost of this gap is specific to the phased rollout. Phase 1 is observation only. The bot does not trade; it watches launches, gathers enrichment data, watches the activity that follows, and the value the bot is producing during this phase is the information it sees. Without a queryable record of that information we cannot do the analytical work that Phase 1 exists to enable: examining which enrichment signals correlate with later token behaviour, computing pass-versus-watch-versus-enter rates against ground-truth outcomes, designing strategies for Phase 2 from real data rather than from imagination. The Phase 1 pipeline is producing the right events; they have nowhere to land.

Phase 2 raises a second class of need. As soon as strategies make decisions, those decisions must be recorded for performance evaluation. As soon as positions open, their current state must be queryable for the position monitor to do its job. These are not pure observation; they are operational state. The data store has to accommodate both, and it has to accommodate the second class without compromising the first.

The expected scale shapes the design. Pump.fun was running roughly thirty thousand token launches per day in 2026 according to industry coverage of the platform. Each detection produces one event with a small payload. Each enrichment produces one event with a RugCheck JSON response that runs five to fifteen kilobytes. Each tracked token produces tens to hundreds of trade observations during its tracking window. A single day's events total roughly one and a tenth million rows totalling roughly six hundred and forty megabytes of uncompressed JSON. Annualised that is between two hundred and two hundred and fifty gigabytes — large enough that a naive "store everything forever" design would fill any Hetzner Cloud plan smaller than the dedicated tier within a year, and large enough that disk strategy cannot be deferred.

The operational target is a single Hetzner Linux server. ADR-004 commits the bot to SQLite accessed through `better-sqlite3` because the database is one file, transactions are atomic, the engine is embedded in the bot's process so there is no network overhead, and the file is trivial to back up. The architecture document is explicit that the bot runs as a single Node.js process on a single machine. None of those choices is reopened here; this ADR specifies what to do *with* that database, not whether to use it.

The store has a small number of universal properties it must satisfy. It must be crash-safe in the sense that an unexpected process termination cannot corrupt the file or produce inconsistent state between an event and its derived projection. It must never block the trading pipeline on the hot path, which constrains how synchronous writes are arranged. It must be the canonical source of truth for "what the bot observed and decided" — not one source among many. It must be queryable for offline analytical work, not only programmatically accessible to the bot itself. It must be backed up continuously, because Hetzner disks are reliable but not indestructible and a money-handling bot whose persistent state can vanish is not a system anyone should run.

The store has a set of equally important properties it must not have. It is not a queue for downstream work; the event bus does that. It is not a cache for external API responses; whatever caching the enrichment layer needs lives in the enrichment layer. It is not a holder of credentials or signing material; ADR-001's wallet adapter owns that with no sharing. It is not an inter-process communication channel; the bot is a single process. Conflating any of these into the store would dilute its single responsibility and introduce coupling the architecture deliberately rejects.

## Decision

The store is a single SQLite database file opened by a single Node.js process and accessed through `better-sqlite3` with the configuration locked in by ADR-004. The connection is opened once at startup, lives for the lifetime of the process, and is closed cleanly during shutdown. There is exactly one writer at any time, which is the bot's process. Tests open separate in-memory databases and never touch the production file.

The database is opened in write-ahead-log mode with `synchronous=NORMAL`. The full PRAGMA baseline applied at connection open is `journal_mode=WAL`, `synchronous=NORMAL`, `busy_timeout=5000`, `foreign_keys=ON`, `cache_size=-20000`, `auto_vacuum=INCREMENTAL`, and `defaultSafeIntegers(true)` on the `better-sqlite3` connection object. Write-ahead-log mode is the durability point chosen across the modern SQLite production guidance: the database remains consistent under all circumstances and remains durable across application crashes; the only loss scenario it permits is the most recent fraction of a second of writes on sudden host power loss. For a single-user bot on a Hetzner Cloud server, that loss window is acceptable and consistent with the rest of the system's posture. The `busy_timeout` value of five seconds protects against transient lock contention from background work like checkpoints and the daily retention prune. The `foreign_keys` flag enforces the relational integrity the schema declares. The `cache_size` setting allocates roughly twenty megabytes of page cache, which is generous for our hot-set size. Incremental auto-vacuuming defers free-page reclamation to explicit `incremental_vacuum` calls rather than holding the database lock for full vacuums; this is important because the daily prune of trade rows will produce free pages that should not require a full vacuum to reclaim. The `defaultSafeIntegers(true)` setting causes `better-sqlite3` to return 64-bit integer columns as JavaScript `bigint` rather than `number`, which is required for round-tripping the lamport and slot fields that the codebase represents as `bigint` per its financial-precision convention.

The schema is organised around two append-only event tables with different retention regimes, plus a small set of mutable projection tables maintained transactionally with each event write. This is the dual-contract pattern: the event tables are the truth, the projections are derived state, and either can be rebuilt from the other at any time.

The first event table, named `lifecycle_events`, captures the events whose value lies in their indefinite history. Detection, enrichment-completed, tracking-closed, and the strategy and position events that will be added in Phase 2 all land here. Each row carries an auto-incrementing global sequence number for ordering, a millisecond timestamp for analytical convenience, an event type discriminator, a `token_internal_id` denormalised for index scans by token, the full event payload as JSON text, and optional metadata. Sequence number provides the canonical "order in which the bot saw events"; timestamps may drift under clock adjustments but the sequence number does not. Lifecycle event volume is roughly ninety thousand rows per day at our scale, producing a few hundred megabytes per day and around one hundred and twenty-five gigabytes per year. This table is never pruned during normal operation.

The second event table, named `trade_events`, captures the high-volume per-trade observations the activity tracker emits. Each row carries the same sequence-number-and-timestamp framing as the lifecycle table, plus typed columns for the fields most often queried in aggregate — token id, trader wallet, side (buy or sell), SOL amount in lamports as an `INTEGER`, token amount as an `INTEGER`, slot, transaction signature — and the full raw payload as JSON text for fields not exposed as typed columns. Trade event volume runs around one million rows per day. This table is pruned on a daily schedule, with rows whose timestamps are older than the configured retention window removed in chunked transactions. The default retention window is ninety days, chosen because Phase 2 strategy backtesting needs at least one full quarter of trade-level granularity to be useful and because ninety days of accumulation fits comfortably within the disk budget of any Hetzner plan from CPX31 upward. The retention number is a tunable, not a structural choice; changing it requires editing one configuration value, not the schema.

The projection tables are small, indexed by natural keys, and updated transactionally as part of each event write that affects them. Phase 1 ships one projection, named `tracked_tokens`, which holds one row per detected token from the moment of detection until tracking terminates. Each row records the token's internal id, mint, launchpad, creator wallet, detection timestamp, enrichment status (`pending`, `completed`, or `failed`), tracking status (`active`, `graduated`, or `timeout`), close timestamp where applicable, and a backpointer to the most recent lifecycle event sequence number that affected the row. Lookups against this table answer the operational queries Phase 1 will actually run — "show me everything currently being tracked", "show me tokens whose enrichment failed", "give me the most recent ten detections" — without folding the event log. Phase 2 will add `open_positions`; Phase 2 strategy work will add `strategy_decisions_summary`; and further projections slot in as they become justified. Each new projection arrives as a new table and a new migration, without affecting the event log or earlier projections.

The store is wired into the rest of the system through a single subscription module named `wireStore`, mirroring the pattern of `wireDetection`, `wireEnrichment`, `wireActivityTracker`, and `wireTelegramNotifications`. The module takes narrow per-event subscribe callbacks as dependencies — `subscribeToDetectedTokens`, `subscribeToAnalysisCompleted`, `subscribeToTradeObserved`, `subscribeToTrackingClosed`, and Phase 2's additions when they arrive — along with a typed `EventStore` interface and the standard clock, logger, and shutdown signal. The wire function is dumb routing; it receives each event from its subscription and calls the corresponding typed method on the `EventStore`. The `EventStore` interface declares one method per persisted event class (`recordDetection`, `recordAnalysisCompleted`, `recordTradeObserved`, `recordTrackingClosed`, and so on). The implementation, named `createSqliteEventStore`, owns the `better-sqlite3` `Database` handle, prepares each statement at construction, runs migrations, and is the only code in the project that imports `better-sqlite3`. This boundary mirrors the contained dependency on `@solana/kit` in `kitSubscriptionSource`: third-party storage primitives stay behind one interface boundary, leaving the rest of the codebase free to evolve without coupling to SQLite specifics.

Schema migrations are managed by a hand-rolled runner driven by SQLite's built-in `PRAGMA user_version` slot. Each migration is a numbered `.sql` file in `src/infrastructure/store/migrations/`, named with a leading zero-padded number and a description (for example `0001_initial.sql`, `0002_add_strategy_decisions.sql`). At startup, the runner reads `user_version`, compares it to the highest-numbered migration file present, and applies each missing migration inside its own transaction. SQLite's data-definition language is transactional, so a migration that fails partway rolls back cleanly and the process exits with an error rather than running on a partially-migrated schema. The runner does not support down-migrations; reverting a schema change is done by writing a new forward-migration that reverses it. This approach is the standard small-project pattern for SQLite and is documented in the SQLite community guidance referenced in this ADR's verification notes.

Event payloads in the JSON text columns use plain JSON, not the binary JSONB format SQLite introduced in version 3.45. Plain JSON is human-readable when the database is inspected from the `sqlite3` command-line tool during Phase 1's expected manual analytical work; JSONB requires function calls to decode and obscures dumps. The disk and parse-time savings JSONB offers are real but small at our scale and are not worth the loss of debuggability. The choice is revisitable if profiling later identifies JSON parsing as a hot path.

Bigint fields, which the codebase uses for lamport values and Solana slots, are stored as native SQLite `INTEGER` columns. SQLite's `INTEGER` type holds 64-bit signed integers and `better-sqlite3` binds JavaScript `bigint` directly to that type without loss. The `defaultSafeIntegers(true)` setting ensures the values come back from queries as `bigint` rather than being silently truncated to `number`. When bigint values appear inside payload JSON columns, they are stringified before serialisation, matching the same convention used at the logger boundary; analytical queries that want to do arithmetic on those values either go against the typed columns or use SQLite's `CAST(json_extract(payload, '$.field') AS INTEGER)`.

The store accepts events through the bus rather than by direct call from publishing modules. The publish-then-persist ordering creates a sub-millisecond window in which a process crash can drop an event after it has been published to the bus but before the store's synchronous handler has written it. This loss window is accepted for Phase 1, where the consequences of losing a single detection or trade event are limited to a gap in the analytical record. For Phase 2 events whose persistence integrity carries higher stakes — `BuyOrderFilled`, `SellOrderFilled`, and any event recording a real-money state change — the execution layer flips the ordering, writing to the store before publishing to the bus. This asymmetric persistence posture mirrors the intent-recording pattern ADR-002 establishes for transaction signing: high-stakes operations are recorded as a precondition for happening, not as a consequence.

The store is continuously replicated to the AWS S3 bucket provisioned for the project. Replication is performed by Litestream running as a separate background process under systemd, streaming write-ahead-log pages to the bucket as they are produced. Litestream's design provides a recovery point objective on the order of seconds — at most a few seconds of writes can be lost on total host failure — and a recovery time objective on the order of minutes to provision a new host and restore. The bot itself is unaware of S3; the replication boundary lives entirely at the operational layer. Bucket access uses a scoped IAM user whose permissions are limited to put, get, list, and delete on the single bucket; broader credentials are not appropriate for a backup target. Object versioning is enabled on the bucket as a defence against accidental overwrites.

The daily retention task runs at a fixed time (defaulting to 04:00 UTC, when Solana mainnet activity is typically lower) and deletes trade rows older than the retention window in chunks of ten thousand. Each chunk is one transaction, allowing other writers to acquire the lock between chunks and preventing the prune from holding the database in an exclusive state. The reclaimed pages are returned to the operating system via `PRAGMA incremental_vacuum` after the prune completes. Failures during the prune are logged but do not stop the bot; the next day's prune will pick up the work.

A second, longer-horizon retention task complements the daily prune. On a quarterly schedule, lifecycle events older than two years are exported to compressed JSONL in the same S3 bucket Litestream replicates to, then deleted from the local table. The export and the delete happen in that order, with the delete gated on a verified upload, so a failed quarterly run leaves the local data intact for the next attempt. The output is one file per archived quarter under a stable path prefix (`archives/lifecycle/<year>-Q<quarter>.jsonl.gz`), readable by any tool that speaks gzip and JSONL and importable back into a SQLite database if a historical analysis ever requires it. The two-year window is a configuration value, not a structural choice; it is chosen because Phase 2 backtesting and Phase 3 strategy retrospectives are expected to use at most the last few quarters of lifecycle data and because two years of accumulation bounds the live database to roughly two hundred and fifty gigabytes, comfortable on any Hetzner plan from CPX31 upward and ample on a dedicated tier. This is the cold-archive companion to the daily prune: same retention-policy shape, longer time horizon, different output destination. Litestream continues to replicate the live database for disaster recovery; the cold archive is a separate concern that bounds the live working set.

## Consequences

The store becomes the canonical record of every event the bot saw and every operational state transition it underwent. Anyone wanting to know what the bot has done queries this database. The structured logs in journald remain the source for operational debugging — what the bot was *doing* in the moments around an incident — but the database is the source for what the bot *observed and decided*. This separation maps the same distinction made between application logs and audit logs in ADR-001.

The dual-contract pattern preserves a complete audit trail at the lifecycle level without paying the cost of folding events to answer current-state queries. The trade-level audit trail is preserved on a rolling window. When the rolling window's bound is reached, the summary contained in each `TokenTrackingClosed` payload remains as the long-term aggregate of what happened during a token's tracking lifetime; the per-trade rows that contributed to that summary are gone. This is an explicit trade. If we later discover Phase 1 analysis benefits from longer trade-level history, the retention window is one configuration knob to extend; if we discover that the summary is sufficient and ninety days is generous, the knob shortens.

The single-file, single-writer architecture is a single point of failure. If the database file is corrupted by a kernel bug, a hardware fault, or a misuse on our part, the bot is unable to start. Recovery is restoration from the Litestream replica. The expected recovery time is minutes. This is acceptable because the bot is a single-user system whose downtime carries no external service-level commitment; high-availability storage architectures such as LiteFS, rqlite, or replicated Postgres would be over-engineering at our scale. The single point of failure is named here so it is not later claimed to have been overlooked.

The retention policy bounds disk growth tightly at both horizons. The trade table is bounded by the daily ninety-day prune, sitting at roughly nine gigabytes at steady state. The lifecycle table is bounded by the quarterly two-year cold-archive cutoff, sitting at roughly two hundred and fifty gigabytes once the archive cycle reaches steady state. Total live database file size therefore grows for the first two years of operation and then stabilises, with old data preserved as compressed JSONL bundles in S3 rather than as live SQLite rows. The Litestream backup of the live file costs roughly five dollars per month and stays flat. The cold-archive bundles add a small further amount that grows linearly with bot uptime but at compressed-JSON density (a quarter of archived lifecycle data is on the order of a few gigabytes after gzip), so the cumulative archive of all historical lifecycle data fits within a few additional dollars per month of S3 storage indefinitely.

The cold archive trades fast historical queries for permanently bounded disk usage. Lifecycle events newer than two years are queryable instantly through SQLite; events older than two years require downloading the relevant quarter's archive from S3 and either inspecting the JSONL directly or importing it into a scratch SQLite database. This asymmetry is the right one for our workflow. Phase 1 and Phase 2 analytical work overwhelmingly uses the most recent quarters; deep historical queries are rare-path operations where a few minutes of manual restore is acceptable in exchange for the live database not growing indefinitely.

The publish-then-persist ordering chosen for Phase 1 events introduces a sub-millisecond window in which a crash can drop an event. The architecture treats this as acceptable for observational events and unacceptable for trading events; the resolution is the asymmetric ordering described in the Decision. The Consequence here is simply that the asymmetry exists and must be respected when implementing the Phase 2 execution layer. Mixing the two postures within a single module would be a design error.

The `wireStore` subscription pattern centralises the question "what does the bot persist" into one file, which makes the persistence story easy to audit and easy to extend. The cost is that adding a new persisted event class requires three coordinated edits — a new method on the `EventStore` interface, a new SQL statement and prepared statement in the implementation, and a new subscription call in `wireStore` — but those are three predictable edits in three obvious places.

The hand-rolled migration runner is intentionally minimal. It is correct for the project's actual scale and adds no third-party dependency. The cost is that we are not getting the niceties of a full migration framework: typed schema, drift detection, dry-run modes. Those niceties are not free even when bundled into an ORM, and the discipline they enforce can be enforced more directly in a project this size by code review and by tests covering migration application. If the project's migration count grows past roughly fifty files or the schema gains tens of tables, we revisit whether a tool earns its weight.

The Litestream replication makes the project's operational story honest. Without it, the only protection against losing every observation the bot has made is the resilience of one Hetzner SSD. Litestream raises that to the resilience of the SSD plus the resilience of S3, which is a meaningfully different number. The cost is a small AWS bill and the discipline of monitoring Litestream's own health.

The store's narrow interface — `EventStore`, returned by `createSqliteEventStore`, used only through `wireStore` — keeps `better-sqlite3` contained at one boundary. The rest of the codebase has no idea SQLite is the storage choice. If a future ADR ever supersedes this one and switches to a different engine, the surface area of change is the store implementation plus its tests. Strategy code, execution code, the position monitor — none of them need touching.

## Alternatives Considered

We considered a pure append-only event log with no projection tables. This is the simplest possible event-sourced shape: one table, every event in it, current state computed by folding events at query time. We rejected this because Phase 2 will introduce modules that need to ask current-state questions — "is this position open?", "is this mint still being tracked?" — at frequencies where folding is impractical. Pure event sourcing requires snapshots and projection maintenance to be added eventually, and adding them later means more work and more migration risk than building them now. The dual-contract pattern is the natural evolution of a pure log when current-state queries are anticipated, and we know they are.

We considered per-domain CRUD tables with no central event log: a `detections` table, an `enrichments` table, a `trades` table, each maintained by a per-domain subscriber, each with a schema shaped to its own query patterns. We rejected this because it contradicts the architecture's central organising principle. The architecture is event-driven precisely because the value of an event flows to many consumers; persisting events as their natural form, rather than as the per-domain shape one consumer happens to want, preserves that property. Per-domain tables also lose the raw external payloads — the full RugCheck JSON, for instance — that the architecture document explicitly says we want preserved for later analysis. The audit story degrades, the analytical story degrades, and we pay the same engineering cost. There is no version of this choice that we prefer.

We considered PostgreSQL. Postgres offers richer query capabilities, robust concurrent write semantics, and a clear scale-out path. We rejected it for the same reasons ADR-004 rejected it: all those benefits address problems we do not have. Postgres is a networked service that becomes its own deployment dependency, runs as its own daemon under its own user with its own permissions, and requires its own backup strategy. A single-process single-user trading bot on a single server does not need a networked database. The day we genuinely outgrow SQLite is the day we have a different bot entirely.

We considered direct calls from publishing modules into the store, where each module both publishes its event on the bus and immediately writes it to the database. We rejected this because it couples every publisher to the persistence layer, defeats the architectural reason the event bus exists, and complicates tests that want to exercise modules without persistence. The publish-then-persist gap this alternative would close is small enough that paying coupling costs across the entire codebase to close it is poor value.

We considered fragmenting the store subscription across multiple wire functions, one per event, so that each subscriber is the absolute minimum width. We rejected this because the gain in narrowness is offset by loss of cohesion. The transactional invariant that an event row and its corresponding projection update happen atomically is easier to enforce when both writes happen in a method of the same `EventStore` implementation than when they are split across subscribers. Adding a new persisted event would also require coordinating edits across more files, not fewer.

We considered the transactional outbox pattern, where each event is written to an outbox table inside the same transaction that produces it, and a separate publisher process reads the outbox and emits events on the bus. We rejected this because the outbox pattern earns its weight in distributed systems where the database and the message broker are separate processes whose joint commit cannot be made atomic any other way. Our event bus is in-process. The atomicity guarantees the outbox pattern provides do not buy us anything that our publish-then-persist ordering does not already buy, with much less complexity.

We considered the `sqlite_zstd_vfs` extension for storing the database in a compressed form on disk. Its readme explicitly warns it is "use at your own risk" and does not yet support WAL mode. WAL is non-negotiable for our durability posture, and "use at your own risk" is incompatible with a system that handles money. The disk-reduction goal the compression VFS chases is met more reliably by the retention policy, which has no impact on durability and no third-party experimental code under our database.

We considered a size-based rotation pattern in which the database file is closed and shipped to S3 once it reaches a fixed threshold (commonly twenty megabytes, in the log-shipping idiom). We rejected this as a primary persistence strategy because logs and databases differ in shape: a SQLite file carries its own indexes, schema version, and projection state, and rotating it at a megabyte threshold would shatter cross-period queries, force every analytical question to UNION across hundreds of frozen files, and turn schema evolution into an archaeology problem. The cold-archive policy described in the Decision captures the legitimate concern under that suggestion — bounded local disk usage — without paying the price of fragmenting the database itself. The retention pattern is the same in spirit; the scale is the right scale (years, not megabytes), and the output is a query-friendly JSONL bundle rather than a frozen SQLite snapshot whose schema may not match the current one when read back.

We considered SQLite's JSONB binary format for payload columns. It is supported since SQLite 3.45, faster to parse, and roughly thirty percent smaller than equivalent JSON text. We chose plain JSON text for Phase 1 because Phase 1 involves us inspecting the database manually through the `sqlite3` CLI to look at raw RugCheck payloads and trace what the bot saw; JSONB requires explicit decode functions and obscures the dumps. The cost of plain JSON in storage is small; the benefit in debuggability during early operation is large. The decision is revisitable if JSON parsing ever shows up as a hot path, which it should not, because the hot path does not parse JSON.

We considered running write operations on a `Worker` thread via `better-sqlite3`'s thread support. We rejected this as a default because our write rate is well within what main-thread synchronous writes can handle: average around thirteen events per second, with bursts on hot tokens reaching a few hundred per second for short windows. Worker threads add coordination overhead and a serialisation boundary between the bus and the writer. They are the right tool when the alternative is event-loop starvation; here it is not.

We considered a query-builder layer such as Kysely or Drizzle over `better-sqlite3`. Both are well-built and would give us typed query construction. We rejected them for Phase 1 because the surface area of SQL the store needs is small and bounded (roughly one prepared statement per `EventStore` method plus a handful of analytical helpers), the codebase already commits in the engineering standards to writing the SQL we run, and adding a query-building dependency to a project where every developer (currently one) is learning the stack means an extra abstraction layer between intention and execution. If the store ever grows beyond a few dozen prepared statements, the question is reopened.

## Implementation Notes

The store lives at `src/infrastructure/store/`, alongside the other infrastructure adapters. Its file layout is the following: `eventStore.ts` declares the `EventStore` interface and exports `createSqliteEventStore`; `wireStore.ts` exports the wire function that connects bus subscriptions to `EventStore` methods; `migrate.ts` exports the migration runner; the `migrations/` subfolder holds the numbered `.sql` files. The store has its own test file at `eventStore.test.ts` covering schema migration application, prepared-statement round-tripping for bigint values, idempotent inserts on duplicate event arrival, projection upsert behaviour for out-of-order events, and rollback behaviour on a forced constraint violation. `wireStore` is covered by `wireStore.test.ts` using a fake `EventStore` to assert the subscription routing.

The database file path is sourced from configuration. In production it is `data/moonscout.db`. In tests it is `:memory:`, sourced from a test-only override. The runtime refuses to open the production path when `NODE_ENV=test`, providing a hard guard against tests accidentally polluting the production database.

Connection setup at startup is a fixed sequence: open the file with `new Database(path)`; apply each PRAGMA listed in the Decision section; call `defaultSafeIntegers(true)`; run the migration runner; prepare every statement used by `createSqliteEventStore`. Statement preparation is eager because the runtime cost is bounded and front-loading it ensures any SQL syntax errors fail fast at startup, not on first hit during operation.

The migration runner reads `user_version`, lists the contents of the `migrations/` directory, parses the leading sequence numbers, and applies each migration whose number is greater than the current version inside a transaction wrapping the file's contents plus the `user_version` increment. A migration whose execution fails causes the transaction to roll back and the process to exit with a clear error. The runner refuses to start if it detects schema objects it did not create, which is a defensive guard against having manually edited the database.

Bus subscriptions inside `wireStore` register with the `AbortSignal` injected from the main entry point. On signal abort, subscriptions are unsubscribed and the `EventStore.close()` method is called to flush the WAL and release the database handle. The order matters: subscriptions are removed before the connection is closed, so no in-flight handler tries to write to a closed connection.

The daily retention task is scheduled by a `setTimeout` chain that computes the next 04:00-UTC boundary, waits for it, runs the prune, and reschedules. The prune runs in a loop of chunked transactions, each deleting up to ten thousand rows from `trade_events` where `occurred_at_ms < ?`, until no rows are affected. After the loop completes, `PRAGMA incremental_vacuum(1000)` is called to return free pages to the operating system. The whole task is wrapped in a try/catch that logs failures at error level without stopping the bot; a single failed prune is not an outage.

The quarterly cold-archive task runs on the same scheduler pattern. It computes the next quarterly boundary (the first day of January, April, July, or October at 05:00 UTC) and reschedules after each run. The task body is a streamed `SELECT` against `lifecycle_events` where `occurred_at_ms` is older than the configured archive window, piped row-by-row through `JSON.stringify` and a `zlib` gzip stream into a local temporary file. Once the file is closed, it is uploaded to the configured S3 bucket under `archives/lifecycle/<year>-Q<quarter>.jsonl.gz` using an S3 client library, with a head-object check after upload to confirm the object exists at the expected size. Only on confirmed upload does the corresponding `DELETE FROM lifecycle_events WHERE occurred_at_ms < ?` run, in chunks of ten thousand rows in the same shape as the daily prune, followed by `PRAGMA incremental_vacuum(1000)`. The temporary file is removed after the delete completes. If any step fails (export, upload, verify, or delete), the local rows remain intact and the next quarterly run picks up the work. The upload is idempotent on the S3 path because the same quarter always produces the same target key; re-running over a partial state writes the same object to the same key without harm. The S3 client library used is the AWS SDK for JavaScript v3 (`@aws-sdk/client-s3`), added as a project dependency at the time this module is implemented and contained to the cold-archive code path so the rest of the codebase does not transitively depend on it.

Litestream is deployed as a separate systemd unit on the production server, started before the bot and stopped after the bot during host shutdown. Its configuration file (`litestream.yml`) declares the database path under `dbs:` and a single S3 replica under `replicas:` with the bucket, region, and a path prefix scoped to this bot. The S3 credentials are loaded from environment variables on the systemd unit's environment, populated from the same `.env` file the bot uses. Restore is performed by stopping the bot and running `litestream restore -o data/moonscout.db <replica-url>`; the runbook for this lives in the operational documentation that the deferred operational-security ADR will formalise.

Test coverage for this module is non-negotiable. The migration runner is covered by tests that apply each migration in sequence against `:memory:` and verify the resulting schema is correct, plus a test that asserts a deliberately-broken migration rolls back cleanly without modifying `user_version`. The `EventStore` implementation is covered by per-method tests that write an event, read it back, and assert the projection was updated correctly. Idempotency is covered by tests that insert the same event twice and verify only one row results. Out-of-order arrival is covered by tests that write a `TrackingClosed` before its corresponding `Detection` and verify the projection is correct after both. Bigint round-tripping is covered by a test that writes a value above `2^53` and asserts it comes back unchanged. The daily retention prune is covered by a test that inserts trade rows on both sides of the cutoff and verifies only the old ones are removed. The quarterly cold-archive task is covered by tests that use a fake S3 client to assert the export-then-delete ordering, the upload-verify-then-delete sequence, and the behaviour when upload fails (rows remain, next run retries with the same key).

When working with Claude Code on this module, the boundary discipline matters more than any specific implementation detail. Generated code that imports `better-sqlite3` outside the store implementation should be rejected. Generated code that bypasses the migration runner to apply schema changes at runtime should be rejected. Generated code that adds methods to the `EventStore` interface without corresponding migration files and tests should be rejected. The store is the project's persistence boundary, and the boundary holds only if the discipline holds.
