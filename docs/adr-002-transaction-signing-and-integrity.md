# ADR 002: Transaction Signing and Integrity

## Status

Accepted. This decision was made during the documentation phase of the project before any code was written. After any code begins depending on this ADR, future changes will be handled by superseding ADRs rather than by editing this document.

## Context

The wallet ADR established the security model around the private key itself. It answered who can request signatures, how the key is protected, and what defenses exist around signing operations. What it deliberately did not address is the integrity of the transactions that flow through the signing gate. The wallet adapter validates transactions before signing them, but the validation is only as good as the rules it applies. If we sign a transaction that looks correct to our validation but does something subtly different from what we intended, the wallet adapter has not failed in its defined role, yet we have lost funds anyway.

This ADR addresses the integrity question at a level the wallet ADR does not reach. It concerns the assurance that what we sign is what we meant to sign, and that nothing has corrupted, tampered with, or substituted the transaction between the moment we constructed it and the moment we cryptographically commit to it.

The integrity question matters most for transactions we did not fully construct ourselves. When we want to swap tokens, we ask Jupiter for a route. Jupiter responds with a serialized transaction template that we are expected to sign. We did not write the instructions in that transaction. We received them from an external service over the network. If Jupiter is compromised, if the network response is tampered with in transit, or if there is a bug in how we deserialize the response, we could end up signing a transaction whose instructions do something other than what we requested. The signature we apply will be cryptographically valid. The transaction will be processed by the network. The funds will move according to the actual instructions, not according to what we thought we were signing.

A second source of integrity risk is timing. Solana transactions reference a recent blockhash that becomes too old to use after approximately one minute. If our signing pipeline takes too long, the blockhash expires and the transaction will be rejected by the network. More subtly, if the transaction was constructed against blockhash A but we sign and submit it after the network has moved on, we may get inconsistent behavior between simulation and execution. The simulation against the older state may show success while the execution against the current state shows failure or a different outcome.

A third source of integrity risk is replay. Solana's blockhash mechanism mostly prevents this, but our internal handling can still create scenarios where a transaction is accidentally signed and submitted twice. If our retry logic for failed submissions does not correctly distinguish between failed-and-not-landed and failed-and-actually-landed, we could end up sending a duplicate transaction with a refreshed blockhash. Defending against this requires careful state management around in-flight transactions.

A fourth source of integrity risk is the transaction structure itself. A swap transaction returned by Jupiter is composed of multiple instructions that together accomplish the swap. We need to verify that the instructions match what a swap should look like. If Jupiter were to return a transaction that included additional instructions beyond what we requested, those instructions would execute alongside the swap, potentially doing things we did not authorize. The validation must look at the full instruction list, not just the top-level swap.

These four concerns motivate the decisions in this ADR. The decisions establish how we verify transaction integrity before signing, how we use simulation as a defensive layer, how we handle timing and replay concerns, and how we integrate all of this with the wallet adapter described in ADR 001.

## Decision

Every transaction that the bot signs goes through a verification pipeline before reaching the wallet adapter's signing operation. The pipeline establishes specific guarantees about the transaction, and the wallet adapter trusts that these guarantees hold for any transaction it receives. This separation of concerns means the wallet adapter focuses on the security boundary around the key itself, while the verification pipeline focuses on the integrity of what flows through that boundary.

The verification pipeline lives in the execution layer of the codebase, not in the infrastructure layer. The reasoning is that verification depends on understanding what the transaction is supposed to do, which is execution-layer knowledge. The wallet adapter cannot verify that a swap transaction is correct because the wallet adapter does not know about swaps. The execution layer knows about swaps, so it owns the verification. The wallet adapter focuses on the universal protections that apply regardless of what the transaction is for.

For transactions involving Jupiter swaps, the verification pipeline begins by recording the intent before requesting the transaction. The execution layer captures the intended trade in a structured form, including the input token, the output token, the input amount, the minimum acceptable output amount based on slippage tolerance, and any other parameters that define what we want to happen. This intent record is what the verification will compare against.

After Jupiter returns the transaction template, the verification pipeline inspects the transaction structure. It verifies that the transaction is well-formed, that it references our wallet as the fee payer, and that the instruction list contains the expected instructions for a swap operation and nothing else. Unexpected instructions cause immediate rejection, regardless of how innocuous they might appear. The principle is that we only sign transactions whose structure matches the pattern we expect.

The pipeline then simulates the transaction against the current network state. The simulation returns the expected outcome including which accounts would change, what the new balances would be, and whether the transaction would succeed. The verification compares the simulated outcome against the recorded intent. The output token must be the one we requested. The amount received must meet or exceed the minimum we specified. The wallet's balance change must match the input amount we authorized. Any deviation between intent and simulated outcome causes rejection.

The simulation also serves as the honeypot defense. If the simulation indicates that selling the token would fail, or that the buy would result in receiving zero tokens, or that some unusual condition prevents normal execution, the transaction is rejected before signing. This applies particularly to buy operations, where we want to confirm we can also sell the token before we commit to acquiring it. The execution layer simulates a hypothetical sell after the buy as part of the verification, and if the simulated sell fails, the buy is rejected.

Only after all verification passes does the transaction reach the wallet adapter for signing. The wallet adapter applies its own validation as described in ADR 001, which is independent of the integrity verification. The two layers are complementary. The integrity verification ensures the transaction does what we intended. The wallet adapter's validation ensures that even if we somehow approved a malicious transaction, it would still be rejected if it violates the universal protections like spending limits.

For timing, the verification pipeline operates within a bounded window. The blockhash used for simulation is the same blockhash used for signing, and the entire pipeline from blockhash retrieval through signing and submission is designed to complete within the blockhash validity window. If the pipeline approaches the window boundary, it aborts and starts over with a fresh blockhash rather than risking submission of an expired transaction. This avoids the inconsistency that would arise from simulating against state A and executing against state B.

For replay protection, the execution layer maintains an authoritative record of every transaction it has submitted. This record is updated synchronously with submission, before the network response is received, so that even if the response is lost or delayed, the record reflects that submission occurred. When retries are needed for transactions whose status is unclear, the execution layer first queries the network for the transaction's actual status using the signature from the original submission. Only if the network confirms the original transaction did not land does the execution layer construct a new transaction with a fresh blockhash and submit it. The original transaction is never resubmitted, because doing so would risk a duplicate execution if the original had actually landed despite the unclear response.

For exit transactions where speed matters more than confirmation, the verification pipeline applies a reduced but not eliminated set of checks. The full simulation is performed, but the comparison against intent is more permissive because exit conditions involve continuously changing prices that may have moved between when we decided to exit and when we sign. The verification accepts a wider range of outcomes for exits than for entries, while still rejecting transactions whose structure or destinations look unexpected. This tradeoff acknowledges that delaying an exit transaction in pursuit of perfect verification can cost more than the verification protects against.

The verification pipeline emits structured events through the event bus that other parts of the system can subscribe to. A successful verification produces a `TransactionVerified` event with details about what was verified. A failed verification produces a `TransactionRejected` event with the reason for rejection. The audit log captures both, providing a complete trail of every signing attempt regardless of outcome. The interface layer can subscribe to rejections to alert the user when transactions are being rejected, which may indicate either an attack or a bug worth investigating.

When verification fails, the failure is treated as a serious signal. A single rejection might be a transient issue. A pattern of rejections, particularly affecting different transaction types, suggests something has gone wrong. The execution layer integrates with the validation failure circuit breaker described in ADR 001, contributing to the failure count that can trigger the circuit breaker. This unified failure tracking ensures that integrity issues at any level contribute to the defensive response.

## Consequences

The verification pipeline becomes the authoritative source of truth about whether a transaction is safe to sign. The wallet adapter's validation remains as a backstop, but the primary defense against malicious or buggy transactions lives in the execution layer. This places significant responsibility on the verification pipeline implementation, requiring careful design and thorough testing. The benefit is that verification logic can use execution-layer knowledge that the wallet adapter does not have access to.

The simulation step adds latency to every transaction. Simulation typically takes a few hundred milliseconds, sometimes more depending on network conditions. For an automated trading bot where speed matters, this is a real cost. We accept it because the alternative is signing transactions without verifying them, which is unacceptable for a system handling money. The latency is bounded and predictable, and the integrity guarantees it provides are worth more than the time it takes.

The intent-recording approach means we cannot retroactively verify a transaction that we did not record intent for. This is acceptable because there should be no transactions in the system that lack a corresponding intent record. If we ever encounter a transaction without intent, that itself is a serious problem worth investigating. The pattern enforces the discipline that every transaction has a clear, recorded purpose.

The bounded timing window for the verification pipeline means that signing takes a predictable amount of time, which is good for system behavior but does mean that under unusual conditions where Helius is slow or the network is congested, we might fail to complete the pipeline within the window and have to start over. The retry logic handles this transparently, but it does mean that some transactions will take longer than their nominal time. We accept this because the alternative of risking an expired transaction is worse.

The replay protection through synchronous record-keeping introduces a small possibility of records that exist for transactions that were never actually submitted, if the bot crashes between recording and submission. This is the safer error direction. A spurious record means we might fail to retry a transaction that should be retried, costing us a missed trade. The opposite error of submitting without recording could result in duplicate submissions, costing us potentially the entire wallet. We choose the safer error direction.

The reduced verification on exit transactions creates a small asymmetry where entries are more strictly verified than exits. We accept this because the operational realities of trading require fast exits, and the consequences of a delayed exit can be larger than the consequences of a slightly less verified exit. The asymmetry is documented and limited; exits still go through structural verification and full simulation, just with more permissive intent comparison.

The unified failure tracking through the circuit breaker means that a buggy strategy producing many invalid transactions could trigger the circuit breaker even though no actual attack is occurring. This is acceptable because a buggy strategy is itself a serious situation that deserves investigation, and pausing the bot while we investigate is appropriate. The circuit breaker thresholds are configured to tolerate occasional rejections from normal operation while triggering on pathological patterns.

## Alternatives Considered

We considered placing the verification pipeline inside the wallet adapter itself, with the adapter understanding swap semantics and verifying them before signing. We rejected this because it would compromise the separation of concerns that makes the wallet adapter trustworthy. The wallet adapter should be focused and minimal. Adding execution-layer knowledge would make it more complex and harder to audit, weakening the security boundary it represents.

We considered skipping simulation for transactions and relying solely on structural verification. Simulation adds latency and depends on the RPC provider responding correctly. We rejected this because structural verification alone cannot detect cases where the instructions look right but the underlying token has unusual behavior, such as honeypots that appear normal in their structure. Simulation is the only way to verify the actual outcome.

We considered a strict mode where any unexpected variation between simulation and intent causes rejection, applying equally to entries and exits. We rejected this because exit transactions face genuine timing pressures where price movement during the verification pipeline is normal and expected. Strict mode would cause exits to fail under perfectly normal conditions. The asymmetric verification is a deliberate accommodation of operational reality.

We considered making the verification pipeline a separate microservice that the execution layer calls. We rejected this because adding network communication between modules introduces failure modes and latency without security benefit. The verification pipeline runs in the same process as the execution layer, with the same trust boundary as the rest of the bot.

We considered using transaction templates that we construct ourselves rather than receiving them from Jupiter. This would let us verify by construction rather than after the fact. We rejected this because Jupiter's routing logic is sophisticated and continuously updated, and replicating it ourselves would be a significant project whose result would be inferior to what Jupiter provides. We accept the dependency on Jupiter and verify what they return rather than building our own routing.

We considered allowing the verification pipeline to be bypassed in certain circumstances such as testing or debugging. We rejected this because creating any bypass mechanism, however well-controlled, increases the risk that the bypass is accidentally used in production or exploited if the codebase is compromised. The verification pipeline is mandatory for all signing operations, with no exceptions.

## Implementation Notes

The verification pipeline lives in the execution layer at a path like `src/execution/verification/`. It is composed of several modules including a structural verifier that checks transaction shape, a simulation driver that handles the simulation interaction, an intent comparison module that checks simulated outcomes against recorded intents, and a coordinator that orchestrates the pipeline.

The intent records are stored in memory during the lifetime of a transaction's processing. They are not persisted to disk because their lifetime is short and their value is operational rather than archival. The audit log captures the verification outcomes, providing the persistent record we need for analysis.

The simulation interaction uses the Helius adapter's simulation endpoint, which is itself part of the infrastructure layer. The simulation is requested with the same blockhash that will be used for signing, ensuring consistency between simulation and execution.

Timing within the pipeline is tracked using the injected clock from the architecture. The clock allows tests to control timing precisely, including testing the case where the pipeline approaches the blockhash expiry window.

The replay protection record is implemented as a structure that maps transaction signatures to their submission state. The structure is accessed under a lock that prevents concurrent modifications, ensuring that the record-then-submit sequence is atomic. The lock is held only for the duration of the record-and-submit operations, not for the full network roundtrip.

Test coverage for the verification pipeline must include the structural checks, the simulation flow with various simulated outcomes, the intent comparison logic with both matching and mismatching cases, the timing behavior at and near the blockhash expiry, and the replay protection under simulated crash and retry scenarios. The simulation tests should use mocked simulation responses, not real network calls.

When working with Claude Code on this module, the verification logic must not be weakened in pursuit of simplicity. Generated code that suggests skipping checks, bypassing simulation, or treating verification as optional should be rejected. The verification pipeline is the primary integrity defense, and any erosion of it undermines the security model.
