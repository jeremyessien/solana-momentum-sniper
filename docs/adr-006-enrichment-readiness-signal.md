# ADR 006: Enrichment Readiness Signal

## Status

Accepted, 20 May 2026. This decision was made after PR #18 shipped the implementation and after PR #19 documented the trigger semantics in the architecture document, but is recorded here because the empirical evidence behind the change and the alternatives considered both belong in the ADR rather than in either of those places. After any further code begins depending on this ADR, future changes will be handled by superseding ADRs rather than by editing this document, in keeping with the convention that accepted ADRs preserve their historical record.

## Context

The enrichment layer needs to call a third-party indexer — Phase 1 ships with RugCheck — for each detected token and assemble the response into a `TokenWithFullContext` that the strategy layer can evaluate. The original architecture had enrichment subscribe to `NewTokenLaunchDetected` and fire its external calls immediately on detection. That ordering looked correct on its face: when a token is launched, ask RugCheck about it.

Empirical investigation in May 2026 showed the ordering was wrong. RugCheck returns HTTP 400 "unable to generate report" for most freshly-launched Pump.fun tokens when called at t=0, the moment the detection event arrives. The error is not a flake; it is RugCheck reporting honestly that its indexer has not yet ingested any on-chain state for this mint. The behaviour is reproducible. We measured it directly with `scripts/investigate-rugcheck-trade-correlation.ts`, which captures fresh Pump.fun mints in real time and probes RugCheck on every observed trade until a full report appears. Across five sampled tokens, about sixty percent transitioned from HTTP 400 to a full report within five hundred milliseconds to two seconds of the first observable trade, and about forty percent took between one and five minutes before becoming queryable. The timing depends on RugCheck's indexer, which we do not control.

Under the original detection-fires-immediately design, this meant approximately forty percent of detected tokens silently had no enrichment record at all. The strategy layer, which is being built on the assumption that every detected token produces a `TokenAnalysisCompleted` event for it to evaluate, would have received decisions for a non-representative subset of tokens. That is the kind of pipeline bug that does not look like a bug in production until the bot starts trading on the subset and discovers, weeks later, that its strategy backtest was run on a different population than its live runs. Phase 1 exists to produce trustworthy data; an enrichment pipeline that drops forty percent of detected tokens does not produce trustworthy data.

The fix has to do two things at once. It has to wait until RugCheck is ready before calling it, and it has to preserve the one-event-per-detected-token guarantee even for the tokens RugCheck never becomes ready for.

## Decision

Enrichment fires on the first `TokenTradeObserved` event for a detected token, not on `NewTokenLaunchDetected`.

The reasoning is direct. A trade existing on-chain is the same precondition for RugCheck's indexer having data. Both depend on the bot's view of the chain reaching a state where there is something to index. The bus already publishes a perfect readiness signal in the form of `TokenTradeObserved`. We use it.

The enrichment layer maintains a per-mint state map keyed by mint address. Each entry is a small state machine with three states: `idle`, `in-flight`, and `succeeded`. On `NewTokenLaunchDetected`, an entry is created in the `idle` state and no external call is made. On `TokenTradeObserved`, the entry for the mint is looked up; if it is `idle` and the cooldown has elapsed (defaulting to one and a half seconds since the last failed attempt), the state transitions to `in-flight` and a RugCheck call is dispatched. On a successful response, the state transitions to `succeeded`, a `TokenAnalysisCompleted` event is published with an `ok` Result for the `rugcheck` field, and a `published` flag is set so the same mint cannot be published twice. On a failed response, the state returns to `idle`, the last error is recorded for later inclusion in the synthetic-err path, and the next observed trade after the cooldown is eligible to retry.

On `TokenTrackingClosed`, the entry is looked up one last time. If `published` is false, the enrichment layer synthesises a final `TokenAnalysisCompleted` event whose `rugcheck` field is an `err` Result — either carrying the last observed error from a failed attempt or a synthetic `network_error` if no attempt was ever made because no trade ever occurred. This is what preserves the one-event-per-detected-token invariant the strategy layer relies on. The entry is then evicted from the state map.

Failures are carried inside `TokenAnalysisCompleted` as the `err` variant of the per-source `Result`, not as a separate event. There is no `TokenAnalysisFailed` event on the bus. This is Principle Seven from the engineering standards ("Errors Are Values, Not Exceptions") applied at the event-bus level. Every subscriber pattern-matches on the snapshot in the same place, whether it succeeded or failed.

## Consequences

Every detected token produces exactly one `TokenAnalysisCompleted` event. The strategy layer can be designed and tested against this invariant without having to handle the case of a detected token that never produces a downstream decision. If the invariant is ever broken — for example by a future change that removes the `TokenTrackingClosed` fallback — the strategy module will silently stop receiving decisions for some tokens, and the failure will not look like a bug at the call site. The invariant is therefore a load-bearing contract; reviewers should treat any change that affects either the trade-trigger path or the tracking-closed fallback as a change to a documented architectural promise.

Tokens with on-chain activity get a real RugCheck snapshot, typically within seconds of the first observable trade. Tokens that never produce an observable trade get an err snapshot at tracking-closed time. There is no third silent-drop state.

RugCheck is called at most once per detected token per cooldown interval. Each call is gated on the existence of a trade we observed ourselves, which means we are never burning API quota on tokens that have no on-chain state for RugCheck to report on. This is the same property a timer-based polling design would aim for, achieved without timers.

The one-and-a-half-second cooldown is a tuning value, not a structural choice. It exists because a token with multiple trades in rapid succession after a failed RugCheck call should not retry on every trade — we want the second call to wait briefly to be polite to RugCheck and to give its indexer time to ingest. The constant lives at the top of `src/enrichment/wireEnrichment.ts` and can be overridden through a constructor parameter for tests. Operational data may argue for a different value over time; the parameterisation is there to make the change cheap when it is justified.

The empirical timing data captured in the Context section is recorded here for posterity but is not load-bearing on the design. If RugCheck's indexer becomes faster, the trade-trigger remains correct because the precondition is still "on-chain state exists." If RugCheck's indexer becomes slower, the same is true. The design depends only on the structural relationship between on-chain activity and indexer readiness, not on the current timing distribution.

The investigation scripts under `scripts/investigate-rugcheck-trade-correlation.ts` and `scripts/verify-enrichment-live.ts` are kept in the repository. They are the empirical evidence behind this decision and the runnable verification that the implementation behaves as intended against the live external service. If a future change re-opens the question — for example, if Phase 2 adds a different enrichment source with different timing characteristics — the scripts are the place to start re-measuring.

## Alternatives Considered

We considered a timer-based retry on detection, in which enrichment fires immediately on `NewTokenLaunchDetected`, treats HTTP 400 as transient, and schedules a retry after a configurable delay via `setTimeout` or `clock.sleep`. We rejected this for two reasons. First, timer-based retry guesses when the external state will be ready, where the bus's own `TokenTradeObserved` event tells us when the external state actually is ready, without guesswork and without unnecessary RugCheck calls during the gap. Second, timer designs in this codebase are an anti-pattern that has been rejected before. The first attempt at this fix used a timer-based retry and was rejected for the same reasons; the principle "use the bus's own readiness signal rather than a wall-clock timer" is now load-bearing guidance and is the kind of thing that should not have to be relearned the next time a similar choice arises. Future modules that need to wait for external readiness should consult this ADR before reaching for `setTimeout`.

We considered firing on detection with an explicit retry loop, transitioning a single per-mint state machine through `idle → in-flight → failed → retry` until success or a configurable timeout. We rejected this because it doubles the state and logic of the state machine to do the same job the trade-trigger does for free. The trade-trigger is the same correctness with less state.

We considered not publishing anything for tokens that never trade, letting them silently fall out of the pipeline at `TokenTrackingClosed`. We rejected this because the strategy layer is being built on the one-event-per-detected-token guarantee. Silent drop would mean some detected tokens have no record of why the bot ignored them, contradicting the Phase 1 framing in the architecture document that "the negative space is informative." If we cannot tell ourselves "this token never produced a tradeable signal and that is itself a data point," we lose part of the value Phase 1 exists to produce.

We considered a separate `TokenAnalysisFailed` event for failures, which is what the architecture document originally described. We rejected this because Principle Seven from the engineering standards naturally extends to the event-bus level: failure is the `err` variant of the same payload that carries success, not a separate channel. Two events would mean every consumer has to subscribe to two streams to know whether a token's enrichment is complete; one event with a `Result`-wrapped payload means consumers pattern-match in one place. The architecture document was edited in PR #19 to reflect this.

We considered polling RugCheck on a schedule until ready — running a background poller for each detected mint, calling RugCheck every few seconds until success or a configured timeout. We rejected this as the worst of both worlds: a timer-based design that also burns external API quota proportional to the count of detected tokens, regardless of whether any of them ever traded. At Pump.fun's launch rate this would be a meaningful fraction of our RugCheck quota spent on tokens that nobody will ever care about. The trade-trigger subsumes the goal of this alternative without the cost.

## Implementation Notes

The implementation lives at `src/enrichment/wireEnrichment.ts` and is around one hundred and sixty-five lines including the dependency types. It is the only file in the project that wires the readiness-signal pattern. Future modules that need similar wait-on-readiness behaviour should follow the same shape: a per-key state map, an idle-in-flight-succeeded state machine, a cooldown between failed attempts, idempotency via a `published` flag, and a fallback at the lifecycle-close event.

Tests live at `src/enrichment/wireEnrichment.test.ts` and cover the full matrix of state transitions: caches on detection without firing, first trade triggers the call, subsequent trades are no-ops once succeeded, cooldown blocks immediate retry, retry succeeds after the cooldown elapses, synthetic err at tracking close for never-traded mints, final err at tracking close carries the last observed error for mints whose attempts all failed, state eviction on close, duplicate-detection no-op, unknown-mint silent ignore on trade, signal-abort cleanup, no-subscribe-if-already-aborted, no-publish-if-aborted-mid-fetch, and full integration through a real bus.

The investigation scripts that produced the empirical evidence are kept at `scripts/investigate-rugcheck-trade-correlation.ts` (the timing measurement) and `scripts/verify-enrichment-live.ts` (the end-to-end live verification). They are runnable against a real `.env` and remain the source of truth for "what RugCheck currently does with fresh Pump.fun tokens" if the question is ever reopened.

When working with Claude Code on the enrichment layer or on any future module that needs to wait for external readiness, the principle to apply is direct: ask whether any event in our own bus signals the same state change you are about to wait for. If yes, subscribe to that event. If no, verify thoroughly that no event-driven primitive exists before reaching for a timer. Timer-based readiness is the anti-pattern this ADR exists to capture.
